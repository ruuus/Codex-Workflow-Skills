# Project Roles

Read this only when a project needs pinned models, reasoning effort, candidate order, or extra rules. Without a project config, the skill uses the global roles `orch_<role>` (installed by `roles.py install-global`, inheriting the global model and effort).

## Config file `.codex/orchestration.json`

```json
{
  "schema": "multi-agent-orchestration/v1",
  "state_dir": ".orchestration",
  "protected_paths": ["data/raw"],
  "startup": {"read": ["AGENTS.md"], "preflight": {"command": "python -m unittest", "result": ".orchestration/preflight.txt"}},
  "rules": ["Raw data under data/raw is read-only"],
  "max_live": 3,
  "dispatch": "named",
  "agent_prefix": "proj",
  "roles": {
    "worker": {"candidates": [
      {"agent": "proj_worker", "priority": 1, "model": "example-model-a", "reasoning_effort": "max-available"},
      {"agent": "orch_worker", "priority": 2}
    ]},
    "reviewer": {"candidates": [{"agent": "orch_reviewer", "priority": 1}]}
  }
}
```

- `schema` is required. If a file at this path lacks it, the scripts fail immediately: it is the project's own orchestration config, and the project's own skill should be used.
- All other keys are optional:
  - `state_dir` defaults to `.orchestration`; it must be inside the project and not the project root;
  - `protected_paths` extends the default protected set (state directory, `.git`, `.codex`, `.agents`, `.env`);
  - `startup.read` lists files the coordinator must read at startup; `startup.preflight` is run once per session turn by the coordinator, and its result becomes a contract input;
  - `rules` go into every contract's `project_rules` and into managed role instructions;
  - `max_live` can only lower the native concurrency limit;
  - `dispatch` is `auto` (default) or `named`; with `roles` it must be `named`;
  - `agent_prefix` defaults to `proj` and cannot be `orch`.
- Validation rejects unknown keys, duplicate JSON keys, duplicate candidates within a role, and booleans posing as integers.

## Candidates

`roles.<role>.candidates[]` requires `agent` and `priority` (integer 0–10; 1 is highest, 0 disables).

- **Managed candidates**: named `<prefix>_<role>` or `<prefix>_<role>_<variant>` (variant is lowercase alphanumerics, optionally separated by underscores). May carry `model`, `reasoning_effort` (a concrete level or `max-available`; requires `model`), and `instructions`. Role files are generated by `roles.py generate`.
- **Reference candidates**: any other name, pointing to a global `orch_*` or hand-written role; they cannot carry `model`, `reasoning_effort`, or `instructions`.

## Selection

Each task selects once at `add-task`, and `start` verifies nothing has drifted:

- With `roles`: among the role's enabled candidates only, take the first **loaded** candidate by priority (ties in written order) and dispatch by name. `requested_agent` can only pick among enabled candidates and cannot bypass priority 0. If no candidate is available, report the gap and stop: no fallback to inline or to global roles. A managed candidate's role file must match the current config (`doctor` shows current).
- Without `roles`: use the global `orch_<role>`. If loaded, dispatch by name; if not loaded and `dispatch=auto`, dispatch inline (default subagent, the contract carries the full role instructions, `degraded_reason` is recorded and the user is told); if not loaded and `dispatch=named`, stop.
- "Loaded" means the names the coordinator copied from the `agent_type` parameter description of the session's dispatch tool, never a listing of files on disk.
- If the config file, role file, role template, or the selected model's catalog entry changes, `start` refuses; tasks that have never started can be `rebind`-ed.

## Generation and drift

```powershell
python -B -X utf8 <skill>/scripts/roles.py generate --root .
python -B -X utf8 <skill>/scripts/roles.py doctor --root .
```

- Generated file `<project>/.codex/agents/<agent>.toml`: `developer_instructions` = role template + project rules + candidate instructions. Read-only roles also get `sandbox_mode = "read-only"`; managed candidates get `model` and `model_reasoning_effort`.
- `sandbox_mode` is advisory only: in testing, subagents kept the coordinator's workspace-write sandbox. Read-only constraints rely on role instructions and the coordinator's after-the-fact checks; do not treat it as permission isolation.
- The first two lines of each file are a generation marker and a body hash. `generate` overwrites only marked files that have not been hand-edited; hand-edited or foreign files are refused; managed files removed from the config are reported, not deleted.
- `doctor` states: `missing` (does not exist), `current` (matches expectation), `outdated` (not hand-edited but differs from the current template or config), `modified` (marked but hand-edited), `foreign` (not generated by this skill).
- After generating or updating, a new session is required to load the roles; then recopy the loaded roles and run `set-loaded-agents`.
- Ask the user for approval before writing the project's `.codex/` or the global `$CODEX_HOME/agents/`.

## Model catalog and reasoning effort

- `model_catalog_json` is read from the effective config: the project `.codex/config.toml` first, then `$CODEX_HOME/config.toml`; relative paths resolve against the directory of the config file that declares them.
- Models are validated against `models[].slug`, and effort levels against `supported_reasoning_levels[].effort`.
- `max-available`: use `max` if the catalog declares it; otherwise take the highest declared level in the order none < minimal < low < medium < high < xhigh < max < ultra; unknown level names are an error.
- Without a model catalog, generation still works but is recorded as `catalog_verified:false`, and `max-available` is unavailable.
- The ledger pins only the normalized hash of the selected model's catalog entry; a changed entry makes `start` refuse.
- Catalog entries and role files only declare the intended configuration; they do not prove the backend actually used that model or effort.

## Context troubleshooting for third-party models

Third-party models reached through a gateway may have context windows and compaction behavior that differ from the catalog:

- First check the catalog entry's `context_window` and `auto_compact_token_limit`, and estimate the size of the contract, input files, and expected output.
- Keep contracts lean: list only necessary inputs and scopes; reference large files by path and hash instead of pasting them into messages.
- On truncated output, repeated compaction, or replies missing fields, first shrink the task (split files or steps) or switch to another candidate in the config; rework still counts against the two-attempt limit.
- Do not automatically change global config, gateway routing, or the model catalog; when an adjustment is needed, describe the symptoms and recommendations to the user.
